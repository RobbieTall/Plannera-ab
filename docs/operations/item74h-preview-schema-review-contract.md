# Item 74H Preview persistence schema review contract

Status: **REVIEWED DESIGN / NOT APPLIED**

This document converts the Item 74H persistence design into a concrete database review contract. It is documentation only. It is not a Prisma migration and must not be executed directly.

## Safety boundary

- Target only Neon project `plannera-ab-db`, branch `preview/agent/item74h-pathway-check` (`br-silent-boat-a74zto1n`).
- The branch must remain a child of `preview/agent/item74f-see-credit` (`br-winter-lake-a7kfbv6z`).
- Production is out of scope.
- Existing tables, columns, rows, prices, purchases, entitlements, credits, and checkout configuration must not be changed.
- No backfill is permitted.
- All new identifiers are generated by the application using the repository's existing Prisma ID convention.
- Generate the real migration from `prisma/schema.prisma`; review it against this contract before applying it.
- Stop if the generated migration contains `DROP`, `TRUNCATE`, an update to an existing row, or an alteration of an existing column.

## Why the schema is additive

The current database already stores:

- a confirmed address, parcel, coordinates, LGA and zone in `SiteContext`;
- LEP instrument and versioned clause evidence in `Instrument` and `Clause`;
- searchable DCP text and numeric metadata in `DCPClause`;
- uploaded evidence hashes and review state in `WorkspaceUpload`;
- generated project outputs in `Artefact`; and
- the exact-scope A$49-to-A$749 credit in `SubmissionSeeCredit`.

It does not durably preserve which versions and values were used by one pathway decision, nor bind that immutable evidence set to all three commercial outputs. Item 74H adds that audit layer without replacing the existing source records.

## Required records

### `SiteSpatialProvenance`

One immutable spatial evidence record for the confirmed site used by an assessment.

Required fields:

| Field | Purpose |
| --- | --- |
| `id` | Application-generated primary key. |
| `siteContextId` | Confirmed `SiteContext`. |
| `authority` | Authoritative spatial publisher. |
| `datasetName` | Dataset or service used. |
| `sourceUrl` | Public source locator. |
| `sourceVersion` | Publisher version/date identifier where available. |
| `retrievedAt` | When the source was retrieved. |
| `effectiveAt` | Date against which currentness was assessed. |
| `contentHash` | Hash of the normalized source response. |
| `matchMethod` | Parcel/address matching method. |
| `parcelId`, `lot`, `planNumber`, `lgaCode`, `zoneCode` | Immutable assessed spatial facts. |
| `latitude`, `longitude` | Assessed point. |
| `payload` | Normalized spatial source response and field-level citations. |
| `trustLevel` | `SITE_CONFIRMED`, `EVIDENCE_VERIFIED`, or `OPERATOR_APPROVED`. |
| `staleAt` | Mandatory recheck boundary when known. |

Idempotency: unique on `siteContextId + contentHash`.

### `PathwayDefinition`

Versioned, authored decision graph for one LGA, zone and proposal type.

Required fields include `versionKey`, `lgaCode`, `zoneCode`, `proposalType`, `status`, `effectiveFrom`, `effectiveTo`, `graphHash`, and `graph`.

- `versionKey` is globally unique.
- `status` is `DRAFT`, `ACTIVE`, or `RETIRED`.
- The first controlled version remains `byron-ru2-shed-v1`.
- A definition cannot silently mutate after an assessment references it; changed logic requires a new version.

### `PathwayAssessment`

The durable result for one project/site/definition/input combination.

Required fields include:

- foreign keys to `Project`, `SiteContext`, `SiteSpatialProvenance`, and `PathwayDefinition`;
- `environment`, fixed to `PREVIEW` for Item 74H;
- `idempotencyKey`, `inputHash`, `evidenceDigest`, and `assessmentVersion`;
- `decision`: `STOP`, `PROCEED`, `MERIT_ASSESSMENT`, or `MORE_EVIDENCE_REQUIRED`;
- `trustLevel`: `GENERAL_GUIDANCE`, `SITE_CONFIRMED`, `EVIDENCE_VERIFIED`, `OPERATOR_APPROVED`, or `SUBMISSION_READY`;
- immutable `input` and `result` JSON;
- `assessedAt`, `staleAt`, `isCurrent`, and optional `supersedesAssessmentId`.

Idempotency: `idempotencyKey` is globally unique. Replaying an identical accepted request must return the existing assessment rather than inserting another one.

Safety: unknown, missing, stale, overlapping, or contradictory evidence may never yield `PROCEED`.

### `PathwayEvidenceSnapshot`

Immutable evidence used by one assessment.

It may reference an existing `Clause`, `DCPClause`, or `WorkspaceUpload`, but must also copy the citation, source URL, source version/date, effective dates, retrieval date, content hash, and normalized excerpt/metadata needed to reproduce the decision if the source record later changes.

Required evidence kinds include `LEP`, `DCP`, `SPATIAL`, `UPLOAD`, and `OPERATOR_NOTE`.

Idempotency: unique on `assessmentId + evidenceKind + contentHash`.

### `PathwayControlSnapshot`

One normalized control value as used by the assessment.

Required fields include:

- `assessmentId` and the supporting `evidenceSnapshotId`;
- stable `controlKey`, label and applicability hash;
- operator/comparator;
- numeric value, lower bound and upper bound using a fixed decimal type;
- text value and unit where applicable;
- land-area-band lower/upper bounds;
- normalized applicability JSON;
- source reference and content hash;
- currentness status and stale date.

Idempotency: unique on `assessmentId + controlKey + applicabilityHash`.

Overlapping applicable controls with different values are a red acceptance result and must not be hidden by selecting one arbitrarily.

### `PathwayGateSnapshot`

Ordered, immutable gate results.

Required fields include `assessmentId`, `gateKey`, `sequence`, `question`, `outcome`, `reason`, `condition`, `evidenceRefs`, and `controlRefs`.

- `outcome` uses the same four deterministic decisions as the assessment.
- `gateKey` and `sequence` are each unique within an assessment.
- A later STOP remains visible even if an earlier gate proceeded.
- Missing evidence is represented explicitly as `MORE_EVIDENCE_REQUIRED`.

### `PathwayArtefactBinding`

Binds the same accepted evidence digest to each customer-facing output.

Required fields include `assessmentId`, `artefactId`, `commercialStage`, `scopeKey`, `evidenceDigest`, and `createdAt`.

`commercialStage` is one of:

- `FREE_PATHWAY_CHECK`;
- `PLANNING_CONTROLS_PACK`; or
- `SUBMISSION_SEE`.

Constraints:

- unique on `assessmentId + commercialStage`;
- an `Artefact` may have at most one Item 74H binding;
- every paid binding must use the assessment's exact `scopeKey` and `evidenceDigest`;
- a stale assessment cannot create a new paid binding.

## Review invariants before application

The generated migration is acceptable only if all of the following remain true:

1. It creates seven new Item 74H tables and their supporting indexes/constraints.
2. It does not alter or delete any existing table, column, constraint, index, enum, or row.
3. It does not introduce a Production connection or environment-dependent SQL.
4. It preserves `STOP`, `PROCEED`, `MERIT_ASSESSMENT`, and `MORE_EVIDENCE_REQUIRED` exactly.
5. It preserves evidence currentness, source version/date, citation, and content hashes as first-class snapshot data.
6. It provides persistent idempotency for assessment replay.
7. It binds one evidence digest and scope to the free, A$49, and A$749 artefacts.
8. It cannot make unknown or stale evidence appear sufficient through a database default.
9. It is generated and reviewed before any Preview application.
10. The parent branch remains unchanged and available as the recovery source.

## Rollback boundary

Before controlled acceptance data is created, rollback may remove only the new Item 74H objects in reverse dependency order:

```sql
DROP TABLE IF EXISTS "PathwayArtefactBinding";
DROP TABLE IF EXISTS "PathwayGateSnapshot";
DROP TABLE IF EXISTS "PathwayControlSnapshot";
DROP TABLE IF EXISTS "PathwayEvidenceSnapshot";
DROP TABLE IF EXISTS "PathwayAssessment";
DROP TABLE IF EXISTS "PathwayDefinition";
DROP TABLE IF EXISTS "SiteSpatialProvenance";
```

Rollback is not automatic and requires the same explicit mutation approval as application. Once a controlled acceptance record exists, preserve or export the audit record before any rollback decision.

## Acceptance evidence after approval

After the reviewed Prisma migration is applied to the isolated Preview branch:

1. compare Item 74H with its Item 74F parent and confirm that only the approved additive objects differ;
2. run the protected synthetic persistence acceptance twice and prove the replay returns the same assessment ID;
3. prove stale, missing, contradictory, and overlapping evidence cannot produce `PROCEED`;
4. run one evidence-confirmed Byron address through the controlled pathway;
5. reload the assessment and prove all evidence, control and gate snapshots remain intact;
6. generate and bind the free Pathway Check, exact-scope A$49 Planning Controls Pack, and A$749 submission SEE to the same scope key and evidence digest;
7. keep checkout disabled and make no Production mutation.
